# Phase 2.5 — Autonomous Character Validation

**Date:** 2026-07-27
**Status:** Approved
**Branch:** feat/wacky-manor-poc
**Depends on:** Phases 0-2 (complete)

## Goal

Validate that LLM characters drive the plot autonomously when given goals
and world observations, without scripted triggers or scene orchestration.

**Verdict gate:** The Hooded Claw discovers the rat poison, schemes to use
it against Penelope, and attempts to execute — all without triggers firing
or scenes being orchestrated. Same 3 rooms, same 5 characters.

## Design Approach

Approach B: reinforce goals in the per-turn observation. Goals are already
in the system prompt via the Eidos renderer (`## Objectives`), but the
system prompt is long and static. Repeating goals in the observation keeps
them in the LLM's active attention alongside the current world state.

No opportunity hints — the observation must not tell the LLM what to think.
If the LLM cannot independently connect "I see rat poison" with "my goal
is eliminate Penelope," that's the signal Phase 2.5 is designed to produce.

## 1. Scenario Mode

### 1.1 ScenarioMode Enum

```java
public enum ScenarioMode { SCRIPTED, AUTONOMOUS }
```

### 1.2 Configuration

`application.properties`:
```
manor.scenario.mode=scripted        # default — preserves existing behavior
manor.scenario.max-turns=60         # autonomous mode only
```

### 1.3 ScenarioOrchestrator Changes

`startScenario(WorldState world, ScenarioMode mode)`:

- **SCRIPTED** — current behavior unchanged. Triggers evaluate after each
  action, scenes fire when triggered, scenario ends on `completeScenario`.
- **AUTONOMOUS** — skip `triggerEvaluator.evaluate()`, skip
  `sceneDirector.runScene()`, use autonomous termination (Section 5).

The REST endpoint that starts scenarios passes the mode from config.

## 2. ObservationBuilder Changes

### 2.1 Method Signature

```java
public static String buildObservation(
    CharacterState character, WorldState world, List<AgentGoal> goals)
```

The orchestrator resolves each character's goals from `AgentRegistry` once
at startup and passes them to `CharacterAgentLoop`, which passes them to
`ObservationBuilder`.

### 2.2 New Section: Your Goals

Appended after `== Your Inventory ==`, before `== Recent Activity ==`:

```
== Your Goals ==
- [PRIMARY] Kill Penelope Pitstop before she finds the treasure
- [PRIMARY] Stay in character as Sylvester Sneekly at all times when others are present
- [SECONDARY] Win the treasure hunt
```

Read from the `List<AgentGoal>` parameter. All goals included (both PUBLIC
and PRIVATE — the observation is per-character, not shared). Sorted by
priority then name, matching the Eidos renderer convention.

### 2.3 New Section: Last Action Result

Appended after `== Recent Activity ==`:

```
== Last Action Result ==
You picked up Rat Poison.
```

`CharacterState` gains a `lastActionResult` field:
- Initial value: `"You have just arrived at Doily Manor."`
- Set by the game loop after `actionResolver.resolve()` using
  `ActionResult.text()` (see §4.5)
- For WAIT actions (which skip the game loop), `CharacterAgentLoop`
  sets `lastActionResult` to `"You waited and observed."` before
  building the next observation
- Read by `ObservationBuilder`

## 3. Narrative Event Descriptions

### 3.1 Problem

Current events are mechanical: `"The Hooded Claw use tea-service"`. Other
characters cannot meaningfully react to this.

### 3.2 NarrativeEventBuilder

A utility that builds public-facing event descriptions:

```java
public final class NarrativeEventBuilder {
    public static String describe(CharacterState character, Action action,
                                   ActionResult result)
```

Rules:
- **MOVE** — `"{name} walked into the {room}."`
- **TAKE** — `"{name} picked up something."` (vague — what they took is
  their business)
- **USE** — `"{name} fussed with the {target} for a moment."` (vague —
  observers see activity, not intent)
- **GIVE** — `"{name} handed something to {target}."`
- **LOOK** — `"{name} examined the {object}."`
- **INTERACT** — `"{name} interacted with the {object}."`
- **WAIT** — no event (doing nothing is not observable)
- **Failed actions** — no event (failed actions are invisible to others)

### 3.3 Character Name for Events

The Hooded Claw's public name is "Sneekly" when in disguise. For Phase 2.5,
use `CharacterState.name()` which is `"The Hooded Claw (as Sneekly)"`.
A future refinement could extract a display name, but for the POC this is
sufficient — the LLM understands the parenthetical.

### 3.4 Integration

The game loop replaces the current string concatenation with
`NarrativeEventBuilder.describe(character, action, result)`. The game loop
checks for null before calling `world.addEvent()`:

```java
String narrative = NarrativeEventBuilder.describe(character, action, result);
if (narrative != null) {
    world.addEvent("action", character.agentId(), character.currentRoom(), narrative);
}
```

This is a behavior change: failed actions and WAIT actions are no longer
visible to other characters in Recent Activity. This is intentional —
failed actions are not observable behavior, and doing nothing is not an
event.

The acting character's own detailed result goes to `lastActionResult` on
their `CharacterState` — they see the mechanical truth, others see the
observable behavior.

## 4. ActionResolver Changes

### 4.1 Auto-Positioning

For all object- and character-targeting actions (`TAKE`, `USE`, `INTERACT`,
`GIVE`), ActionResolver sets the acting character's x-position to the
target's x-position before resolving:

- Object targets: `character.setX(obj.x())`
- Character targets (GIVE): `character.setX(target.x())`

This replaces the proximity check. `isWithinProximity()` and
`PROXIMITY_THRESHOLD` are removed from ActionResolver — with
auto-positioning, distance is always zero, making the check dead code.
The x-position model stays for rendering and WebSocket position events.

Without auto-positioning, characters entering a room land at x=0.5 (via
`WorldState.moveCharacter()`) and cannot reach objects at other positions.
Existing proximity-failure tests (`interact_just_beyond_proximity_threshold_fails`,
`give_to_character_too_far_away`, `proximity_check_rejects_distant_interaction`)
are replaced with auto-positioning tests that verify the character's x is
set to the target's x after action resolution.

### 4.2 TAKE — Object Removal and Item ID

**Object removal:** `resolveTake` marks the taken object as removed via
`world.markObjectTaken(action.target())`. Subsequent queries through
`WorldState.visibleObjects()` and action resolution filter out taken
objects. This prevents duplicate takes and ensures the object disappears
from the room.

If the object has already been taken (`world.isObjectTaken(action.target())`),
`resolveTake` returns `Failed("... is no longer here.")`.

**Item ID mapping:** `GameObject` gains an optional `itemId` field that
specifies the inventory ID when the object is taken. Defaults to the
object key if absent. `resolveTake` uses `obj.itemId()` instead of the
current hardcoded `poison → rat-poison` mapping.

`rooms.yaml` update:
```yaml
poison:
  name: "Rat Poison"
  itemId: rat-poison
  portable: true
  visibleTo: [hooded-claw]
```

### 4.3 USE — Item Consumption and Effect Application

`resolveUse` performs all state mutations internally, consistent with how
every other action type works in ActionResolver:

1. Remove `withItem` from character's inventory
2. Call `world.applyEffect(action.target(), action.withItem())`
3. Return `ActionResult.Success(description)`

No new `ActionResult` variant is needed. The game loop does not participate
in USE state mutation — ActionResolver already receives `WorldState` and
mutates it directly for MOVE, INTERACT, and GIVE.

### 4.4 WorldState Additions

**Taken objects tracking:**
```java
private final Set<String> takenObjects = new HashSet<>();

public void markObjectTaken(String objectId) {
    takenObjects.add(objectId);
}

public boolean isObjectTaken(String objectId) {
    return takenObjects.contains(objectId);
}
```

`visibleObjects()` filters out taken objects before visibility checks.

**Object resolution in ActionResolver:** All resolvers that look up objects
from `room.objects()` (`resolveTake`, `resolveUse`, `resolveInteract`,
`resolveLook`) must check `isObjectTaken()` after the lookup. If taken,
return `Failed("... is no longer here.")`. This is centralized via a
helper:

```java
private GameObject findLiveObject(Room room, String objectId, WorldState world) {
    GameObject obj = room.objects().get(objectId);
    if (obj == null || world.isObjectTaken(objectId)) return null;
    return obj;
}
```

All object-targeting resolvers use `findLiveObject()` instead of direct
`room.objects().get()`. A null return produces the same `Failed("No such
object")` response as a nonexistent object — from the character's
perspective, a taken object is gone.

**Applied effects map:**
```java
private final Map<String, Set<String>> appliedEffects = new HashMap<>();

public void applyEffect(String objectId, String itemId) {
    appliedEffects.computeIfAbsent(objectId, k -> new HashSet<>()).add(itemId);
}

public boolean hasEffect(String objectId, String itemId) {
    return appliedEffects.getOrDefault(objectId, Set.of()).contains(itemId);
}
```

Generic mechanism — not tea-specific. Phase 2.9 uses the same for dynamite
on staircases, blades on treasure chests.

### 4.5 ActionResult.text() Accessor

Add a common `text()` method to the `ActionResult` sealed interface so
all variants expose their human-readable description through one accessor:

```java
public sealed interface ActionResult {
    String text();

    record Success(String description) implements ActionResult {
        @Override public String text() { return description; }
    }
    record Failed(String reason) implements ActionResult {
        @Override public String text() { return reason; }
    }
    record MovedToRoom(String roomId, String description) implements ActionResult {
        @Override public String text() { return description; }
    }
    record ItemReceived(String itemId, String description) implements ActionResult {
        @Override public String text() { return description; }
    }
}
```

The existing `SceneTriggered` variant is removed — it has zero references
in the codebase and is dead code. Scenes are orchestrated through
`SceneDirector`, not through `ActionResult`.

This eliminates pattern matching when extracting result text (e.g., for
`lastActionResult`).

## 5. Autonomous Termination

### 5.1 Turn Counter

Each action resolution increments a global counter (across all characters).
With 5 characters and `maxTurns=60`, each character averages ~12 actions.
When `maxTurns` is reached, the scenario ends with `TURN_LIMIT`.

### 5.2 Termination Check

The check lives in the game loop, after action resolution and before
`pending.complete(result)`:

After each action resolution, check:
- `world.hasEffect("tea-service", "rat-poison")` → `POISONED`
- Global turn counter ≥ `maxTurns` → `TURN_LIMIT`

### 5.3 Completion Reason

```java
public enum CompletionReason { POISONED, TURN_LIMIT }
```

`WorldState` changes:
```java
private volatile CompletionReason completionReason;

public void setScenarioComplete(CompletionReason reason) {
    this.completionReason = reason;
    this.scenarioComplete = true;
}

public CompletionReason completionReason() { return completionReason; }
```

`ManorWebSocketEvent` gains a `reason` field. The `scenario` factory
becomes `scenario(String status, String reason)`:

```json
{ "type": "scenario", "status": "completed", "reason": "poisoned" }
```

The `"started"` event passes `null` for reason.

### 5.4 Evaluation Criteria

For Phase 2.5 verdict:
1. Did HC find and take the poison? (observable from events)
2. Did HC use the poison on the tea? (terminal: `POISONED`)
3. Did anyone intervene? (events showing foiling behavior)
4. Did it hit the turn limit without resolving? (`TURN_LIMIT` — failure signal)

Sub-distinctions within `TURN_LIMIT` (HC never found poison vs. HC took
but never used) are observable from the event log and do not require
separate `CompletionReason` values. A future `FOILED` reason requires
intervention mechanics (DROP, STEAL, character cooperation) — tracked
as GitHub issue (TODO: file on `mdproctor/examples` — gh auth was
unavailable during review).

## 6. What Doesn't Change

- **Eidos descriptors** — goals, constraints, briefings, templates stay
  as-is. If autonomy fails, fix descriptors, not the engine.
- **Qhorus channels** — same channel structure, same dispatch.
- **WebSocket protocol** — existing event types unchanged. `scenario`
  event gains optional `reason` field (backward compatible).
- **SceneDirector, SceneContext, scenes.yaml, triggers.yaml** — all
  preserved. Scripted mode uses them unchanged.
- **CharacterAgentLoop** — same loop structure. Only its inputs change
  (observation content).
- **Frontend** — no UI changes for Phase 2.5.

## 8. Test Plan

### Unit Tests

- `ObservationBuilderTest` — goals section renders correctly, last action
  result renders correctly, goals sorted by priority
- `NarrativeEventBuilderTest` — each action type produces the right
  narrative, failed actions produce no event, WAIT produces no event
- `ActionResolverTest` — USE consumes item from inventory, USE applies
  effect to WorldState, USE with invalid item still fails correctly,
  TAKE marks object as taken, second TAKE on same object fails, TAKE
  uses `obj.itemId()` for inventory, auto-positioning sets character x
  to target x, actions on taken objects fail with "no longer here",
  existing proximity-failure tests replaced with auto-positioning
  verification tests
- `WorldStateTest` — `applyEffect`/`hasEffect` works, `markObjectTaken`/
  `isObjectTaken` works, `visibleObjects` excludes taken objects
- `ActionResultTest` — `text()` returns correct value for every variant

### Integration Tests

- `AutonomousScenarioTest` — run autonomous mode with a mock LLM that
  returns scripted JSON responses simulating HC taking poison and using
  it on the tea. Verify: poison consumed from inventory, effect applied
  to tea-service, scenario completes with `POISONED` reason. Also verify:
  no triggers fired (`world.hasTriggerFired(*)` false for all trigger IDs),
  no scenes completed (`world.isSceneCompleted(*)` false for all scene IDs),
  no narrator events in the event log.
- `ScriptedModeUnchangedTest` — run scripted mode, verify triggers and
  scenes still fire as before (regression guard).
- `TurnLimitTest` — mock LLM returns only WAIT actions, verify scenario
  ends at turn limit with `TURN_LIMIT` reason.

### LLM Evaluation (llm-eval profile)

- `AutonomousCharacterEvalTest` — run full autonomous scenario with live
  LLM. Log all events. Manual verdict: did HC scheme and attempt to
  poison the tea? This is the Phase 2.5 verdict gate.
